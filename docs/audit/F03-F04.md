# F03/F04 — Explicit live-source generations

Active serving records the actual source HEAD and materialized overlay commit during preparation. Watchers are installed before reconciling that recorded generation with current source state. Active Git index, HEAD and refs are watched, including linked-worktree Git directories. Access events are ignored, and event debounce has a bound so a busy producer cannot postpone updates forever.

A private staging repository retains raw merged input, including omitted proposals. It is cloned once at startup, not per edit. Ordinary edits copy affected tracked paths; clean HEAD transitions reconcile the full active inventory. New Git objects are fetched only from the local source when needed. Sibling content remains the startup snapshot and conflicting active edits fail rather than silently winning.

Target selection intent is separate from its changing Markdown/asset inventory. Newly staged assets, renamed paths and selected deletions are accounted for. Untracked additions remain excluded; unstaging an uncommitted addition removes it from prepared input. A changed Build.toml requires an explicit restart instead of partially re-resolving source policy.

Preprocessing occurs outside Zola's watched tree. Parsing/transform failures retain last-good input, including repeated retries, and subsequent valid input recovers. Publication I/O is NOT an atomic multi-file Zola transaction: a copy failure is explicitly diagnosed as potentially partial and paths remain pending for retry. This candidate does not claim last-good HTML for every Zola template/runtime error. Filesystem isolation is the separate F01 candidate and must also be included before a hardened rollout.

## Executable acceptance

```
python3 tests/serve_generation.py --build-eips /absolute/candidate/build-eips --evidence /new/scratch/path
```

This launches real loopback Zola servers and exercises create/stage/unstage without unrelated edits, clean branch transitions in both directions, linked Git worktrees, targeted asset creation/rename, invalid-update retention and recovery, selected deletion/restoration, sibling collisions and manifest-change diagnostics. Processes are always terminated in finally blocks. Rust tests additionally cover startup reconciliation, source index preservation and event filtering. This process-group test is POSIX-specific; native Windows watcher acceptance remains outstanding.
